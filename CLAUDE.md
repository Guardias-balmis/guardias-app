# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Guardias · Dr. Balmis — an on-call-shift ("guardia") scheduling tool for Radiodiagnóstico residents at Hospital General Universitario Dr. Balmis. Architecture: domain-driven design, Google Sheets as both datastore and deliverable, a Google Apps Script Web App backend, and a no-build-step React client loaded via Babel Standalone in the browser. Guiding goal (README.md): the app must run ≥10 years with no administrator — R1–R4 levels are derived from dates rather than stored, history is never deleted, and no secret ever lives in the browser. The one exception to «no administrator», a developer-admin window, expires by itself on a fixed date (V-16 bullet below); any future exception must expire the same way, never depend on someone remembering to remove it.

The "v2" rewrite is live: `main` served the old v1 client until the cutover on 2026-07-24, and now serves this codebase. Residents are testing it in production against the real Sheet, so treat anything reaching `main` as reaching them.

Shift-code vocabulary used everywhere (domain, UI, Sheets) — never translate or rename: `G` guardia ordinaria · `GF` guardia festiva · `GP` guardia prefestivo · `3P` tercer puesto (voluntario) · `V` vacaciones · `R` rotación externa · `B` baja · `C` congreso (V-62). A trailing `*` (`G*`) is not a code: it marks a cedida/comprada (`asignaciones.origen`); `projection.js` writes it into the monthly tab so its exact-text COUNTIF/SUMPRODUCT skip it, `Calendar.jsx` shows it, but `asignaciones.codigo` never holds it. V-58 retired V-56's `REFUERZO`/`G+`: a day's third person is always a `3P`. A day's people (INV-1, INV-8e) are its G/GF/GP only (`validate.js`'s `GUARDIA`, hand-copied elsewhere — see «Domain layer»; unlike INV-8e, `router.js`'s `extras` rules count a fixed 3P as a person); `OCUPA_PUESTO` adds `3P` because it measures presence (INV-5/7/15): don't merge the two sets.

There is no lint script and no bundler for the client. `npm test` covers domain, server, most of `client/lib/*.js` (`client/lib/test/`) and the repo-wide gates in `test/` via `node:test`; the `.jsx` screens are **not** Node-testable (Babel-in-browser) and are verified manually in-browser instead — this is intentional, not a coverage gap to "fix". So in new code, logic a screen needs that can be wrong (a fetch range, an aviso's text, a card's state) goes in a tested `client/lib/*.js` module, not inline in the `.jsx`; `Calendar.jsx` still computes some fetch ranges inline (festivos ±1 day; C-2 history's end bound, not its start) — not a refactor to sweep.

**`--test` file-selection args must be UNQUOTED globs — never quoted, never a bare directory (2026-08-08 incident).** Node expands a quoted glob (`'v2/domain/test/*.test.js'`) itself only from Node 21, so on Node 20 (the documented minimum) it silently finds zero tests; a bare directory is walked recursively by Node 20 but finds nothing on Node 22+ (verified in `node:20`/`22`/`24` containers). An unquoted glob works on every version because the *shell* expands it into file paths before Node sees a wildcard. `package.json`'s `test`/`push`/`deploy` scripts and CI (`.github/workflows/test.yml`, pinned to Node 20) rely on this — don't "clean up" the globs: both alternatives silently zero out the suite on some Node version.

## Architecture

### Domain layer (`v2/domain/*.js`) — the source of truth

Zero-dependency, zero-I/O ES modules. All sixteen reach Apps Script via a generated bundle (`build/build-gas.mjs`'s `DOMAIN_MODULES`); the browser imports only the nine domain modules `index.html` modulepreloads (its `v2/domain/*` entries), so a fix in server-only `apply`, `blockPreview`, `holidays`, `imaginaria`, `projection` or `responsible` reaches residents with the Apps Script redeploy, not the push to `main`. That list is hand-kept and topological (a module imports only modules listed before it) — which is why `apply.js`, listed third, copies `validate.js:OCUPA_PUESTO` as `FIJABLES`; it is one of many untested hand copies of the codes (G/GF/GP/3P in `router.js`, `ai-prompt.js`, `Calendar.jsx`, `design-tokens.js`; G/GF/GP across `v2/domain`): before adding or changing a code, grep `"GF"` across `v2/domain`, `server/src` and `client` — don't trust a list. A new module left out of the list that no listed module imports passes in the browser and `npm test` (`parity.test.js` only walks the list; an import from a listed one fails loudly) but is `… is not a function` in production; add it also to the hand-kept `DOMAIN` in `server/dev-server.mjs`.

Governing principle (spec.md §1): **derive, don't store**. A resident's level (R1–R4/PENDIENTE/FINALIZADO) is never a persisted field — it's computed on demand from the resident's training periods (`levelOn(periodsOfResident(r), fecha)`, `residents.js`). There is no "promote resident" action; the level changes when the next period starts — the anniversary unless the periods were edited (V-24). Always derive through `periodsOfResident`, never from `fechaInicio`; on the server read residents through `router.js:allResidentes` (the only one that hydrates edited `periodos`); and never rebuild a resident without its `periodos` (`validate.js:buildMonthContext` projects residents field by field, so a new field goes there by hand). Any of the three silently gives one resident two levels. Residents are never deleted — a `FINALIZADO` resident simply stops appearing in level-filtered views while their full history stays intact. The same append-only philosophy applies to `Bloqueo` cancellation (re-insert same id with `activo=false`, never delete the row) and to `Cuadrante` state transitions (append-only history rows).

Dates are always ISO `"YYYY-MM-DD"` strings, validated strictly by `calendar.js:parseISO`, with all arithmetic through `Date.UTC(...)` — never the local-timezone `Date` constructor — and **months are 1–12 everywhere**, never JS's native 0–11. It exists to make a real v1 bug impossible (a +1-month offset from `Date.getMonth()`): never hand-roll `new Date(anio, mes, ...)`, always go through `calendar.js` helpers.

`Bloqueo` (motivo BAJA | VACACIONES | ROTACION | CONGRESO) is deliberately split from `Preferencias.fechasEvitar`: only `motivo=BAJA` is DURO (hard) and blocks assignment (INV-5); VACACIONES/ROTACION/CONGRESO are informative — they never block by themselves but still feed INV-6 and P-13, INV-2 (not ROTACION), INV-7 (nearby ROTACION) and `puentesLibres` (V-27); INV-3's availability discount is BAJA only. `fechasEvitar` is pure soft preference and is never enforced by the validator. Don't collapse these into one table.

**Toda lectura de `bloqueos` pasa por `v2/domain/absences.js` (decisión V-19).** Los criterios de
cada invariante son distintos a propósito y están nombrados allí (`BLOQUEA_ASIGNACION` para INV-5,
`EXIME_DEL_MINIMO` para INV-2, `AUSENCIA_SIMULTANEA` para INV-6 y P-13, `DESCUENTA_DISPONIBILIDAD`
para el descuento de INV-3, `AUSENTE_EN_PUENTE` para `puentesLibres`, `isNearbyRotation` para INV-7): no escribas un `filter` nuevo sobre `motivo`,
usa el conjunto que corresponda. El descarte de las filas canceladas (`activo=false`) vive ahí y
solo ahí — cuando vivía en el router, bastaba un invocador que no pasara por él para que un bloqueo
cancelado volviera a bloquear asignaciones. Y recuerda que **una «B» en la rejilla no es una
ausencia**: es un código de asignación que no lee ningún invariante. La ausencia real es una fila de
`bloqueos`, que desde V-19 puede crear y cancelar también por otro residente quien tenga el permiso
del ciclo (`requireCicloPermiso`). Desde V-50 `crearBloqueo` pinta además la marca V/R/B/C
(`router.js:writeBloqueoMarcas`) solo en celdas VACÍAS y nunca en un mes PUBLICADO —dos guardarraíles
que no se quitan—, y `cancelarBloqueo` no la borra: nunca deduzcas una ausencia de la marca. Para el
generador con IA, en cambio, es dura: proponer guardia sobre V/R/B/C es FORMATO (`apply.js:pisadosDe`; la tarjeta promete conservar las marcas, spec.md §7),
aunque V-8 no bloquee vacaciones ni rotación. El prompt se contradice: `ai-prompt.js:seccionMarcadores` prohíbe la celda marcada
y `seccionBloqueos` la permite sin alternativa; ninguna fila de §6 lo concilia con V-8, así que si tocas un lado, decídelo. `MARCADORES_REJILLA` está copiado
a mano en `apply.js` y `router.js`, sin test: un código de marca nuevo va en los dos y en `router.js:ASIG_CODIGO_DE_BLOQUEO`/`ASIG_CODIGOS`.

The seventeen modules split cleanly by responsibility: date/weekday/UTC arithmetic and academic-year derivation (`calendar.js`); the Comunitat Valenciana base holidays, `valencianHolidays` (`holidays.js`, V-61 — only `router.js:festivosEfectivos` reads it); training periods, level, and group derivation (`residents.js`); a deliberately dumb per-resident shift counter that never sees holiday data (`tally.js`, through which INV-4 reaches equity: any truthy `origen` — cedida/comprada, whitelisted by `router.js:ASIG_ORIGENES` — goes to its own counter, out of the equity axes and dobletes; keep the truthiness test, V-58 relies on it for leftover `REFUERZO` rows. Presence checks read `codigo` alone on purpose: a cedida is still someone on shift); the single reader of the `bloqueos` table, `absences` (`absences.js`, V-19); preventive coverage-risk simulation on `Bloqueo` registration, `previewBloqueoRisk` (`blockPreview.js`, P-13 — a pre-check at `crearBloqueo` time, not a `validateMonth` invariant); the derived Imaginaria queue, `imaginariaQueue` (`imaginaria.js`, V-20 — a tool, never called by `validateMonth`); the month-scope invariant validator, `validateMonth` (`validate.js` — "la IA propone, el validador dispone"); third-post rules, `validateThirdPost`/INV-8 (`thirdpost.js`); equity at the two closes INV-3 defines — `validateResidencyYearClose` (residency year, all six axes) and `validateQuarterClose` (quarter, `total` only; P-8/V-13), both `aviso`-only — plus INV-4 (`equity.js`); the responsable lottery, INV-14 (`responsible.js`); cuadrante state-transition rules only, no persistence (`cuadrante.js`; its `stateAfterEdit` is only the default — see «Lo opcional no invalida» below); Sheets-ready row projection that writes nothing itself (`projection.js`); the AI generator's write plan, `monthCompletionPlan`/`monthReplacementPlan` (`apply.js`, V-45/V-47 — computes what to write and writes nothing; only the server calls it); the accumulated per-resident tally, `accumulatedTally` (`accumulate.js`); the write plan for the service's own Excel, `buildContajePlan` (`contajeExcel.js`, V-65 — generic sheet operations plus header fingerprints; it touches no sheet, `Code.gs` applies them blindly); and the deterministic month generator, `generateMonth` (`schedule.js`, V-34 — **propone**, no valida: su coste imita a `equity.js` pero el juez sigue siendo el validador). Since V-45 only its tests call it (production uses `generarCuadranteIA`), and it predates V-55/V-58: it is the fallback V-45 accepted losing (without AI the service falls back to the manual grid). Don't delete it as dead code, and don't assume a fix there reaches residents.

Load-bearing contracts, easy to silently break:
- **C-1 (lookahead):** any monthly `dobletes` computation that gets summed across months (equity accumulation, `accumulatedTally`) must feed `tally()` the target month's assignments **plus** the first ~2 days of the next month, or a Friday-31→Sunday doblete silently vanishes — the bug S-5 already fixed once. The residency-year close's month contribution is one: `router.js:closeViolations` and `client/lib/closes.js` pass the next month's first two days too (2026-09-07: before, whoever closed on Friday the 30th lost that doblete; an earlier-closing cohort-mate kept it). The Sheets projection never goes through `tally`: `projection.js`'s per-tab doblete formulas see only their own month and "Resumen" sums them, so both deliberately lose that doblete (S-5, matches the legacy `.xlsm`) — don't "fix" that without re-reading its header comment. The **official** count is the other deliverable: the service's Excel (`contajeExcel.js`, V-65) does go through `tally` with the lookahead, but only over PUBLICADO months, so that doblete appears once the next month is published; when the two disagree, the Excel wins.
- **C-2 (INV-7 rotation history):** INV-7 is evaluated only in the month a nearby rotation *ends*, but needs that resident's assignments for the whole rotation, which may start in an earlier month. Callers must fetch that history themselves — use `validate.js`'s exported `rotationHistoryStart` helper rather than reimplementing it (a past regression: Calendar.jsx was not honoring this).
- **El ciclo del cuadrante no depende de que exista un Responsable (decisión V-16).** `requireCicloPermiso` (server/src/router.js) gatea publicar/despublicar, el sorteo del Responsable (no `sortearEvento`, abierto a propósito), registrar/anular excepciones e imaginaria (leerlas no), confirmar la revisión anual de festivos (V-63; cargarlos o anularlos no), `generarCuadranteIA`, las fechas y periodos de cualquiera (también los propios) y las ausencias de otro: lo tiene el titular del mandato vigente y, si no hay ninguno, cualquier Mayor (R3/R4). Relee el store en cada llamada: no te fíes de `session.rol`, que se firmó en el login y puede ser anterior al sorteo. No inventes un mandato para desbloquear nada — INV-14 exige R3 a 1 de enero y el registro tiene que seguir siendo verdad. **El permiso de validar va aparte, y su restricción caduca sola.** `marcarValidado` y aprobar solicitudes de acceso pasan por `requireValidarPermiso` (V-52): hasta `FECHA_LIMITE_ACCESO_DESARROLLADOR` (2027-03-31, inclusive) solo los administradores —residentes con email en `EMAILS_ACCESO_DESARROLLADOR` (V-49), que además pasan todo `requireCicloPermiso`—; después cae solo en `requireCicloPermiso`. Para ampliar, mueve la fecha; nunca quites la caducidad. Ambas constantes están copiadas a mano en `client/lib/permisos.js` (espejo solo para la UI) sin test que las compare: cambia las dos.
- **Solo bloquea lo imposible y lo ilegal (decisión V-14).** De los invariantes que juzgan el cuadrante, solo cuatro dan `error` e impiden pasar a VALIDADO (INV-14 también es `error`, pero juzga el mandato, no el mes): INV-1 (día sin ninguna G/GF/GP; la composición del día —dos Mayores, dos Pequeños, tres guardias— es `aviso` desde P-14/V-56; el 3P no cuenta ni para cubrir el día ni para la composición, ver el vocabulario), INV-5 (guardia sobre una baja médica), INV-11 (R1 asignado en junio-agosto) e INV-15 (dos guardias en días consecutivos). Los cuatro son «imposible» o «ilegal»: INV-15 entró como `error` en V-35 por eso —el descanso tras una guardia de 24 h es obligación legal, como la baja de INV-5—, no como excepción. Todo lo demás es `aviso` — equidad (INV-3, INV-8), recuento mensual (INV-2), ausencias simultáneas (INV-6), cobertura de rotación cercana (INV-7), 2×R2 sin justificar (INV-9), eventos (INV-10). El motivo es estructural: una regla que bloquea por algo que no se corrige dentro de la herramienta deja al servicio sin cuadrante el día que nadie sepa desbloquearla, y el proyecto debe sobrevivir sin administrador. No "arregles" esto subiendo una a `error`: la contrapartida acordada es que la UI pide confirmación explícita («Validar de todas formas») solo ante avisos de equidad —`cuadrante.js:EQUITY_INVARIANTS` (INV-3, INV-8 y el recuento de verano de INV-11), filtrados con `equityWarnings`, nunca reconociendo el mensaje por su texto— o cuando un cierre o INV-8 no se ha podido comprobar. El resto de avisos (INV-2 incluido, a propósito) no la piden: no los metas ahí. La 8e de V-58 es prioridad de cobertura, no equidad, y pide la confirmación —que V-58(b) exige— solo porque lleva el id `INV-8`: no le des uno propio.
- **Lo opcional no invalida un mes VALIDADO (V-58d).** `cuadrante.js:stateAfterEdit` (toda edición devuelve VALIDADO a BORRADOR) es solo el defecto: `router.js:guardarAsignaciones` deja el mes VALIDADO si TODO el lote escribe `3P` en celdas VACÍAS o vacía celdas `3P` (el 3P añadido se rechaza solo por un `error` NUEVO); cualquier otro cambio invalida. La otra excepción, la fase `extras` del generador, está en «Generador con IA». La regla vive solo en el servidor: `guardarAsignaciones` devuelve `estados` y `Calendar.jsx` los lee (`stateAfterEdit` solo para un `/exec` antiguo) — no la repliques en pantalla.
- **Un solo cuadrante mensual (decisión V-15).** Los «2 grupos» y sus «cuadrantes provisionales» de la normativa son la regla de composición Pequeño+Mayor (INV-1) y la organización de cada grupo, no dos unidades de datos: no hay ni habrá un cuadrante por grupo, ni dos pestañas.
- **C-4 (histórico de INV-8):** el ciclo L-D del tercer puesto (INV-8b) **se cuenta dentro del año
  de residencia de cada uno** (P-16, decisión V-55): se reinicia al empezar otro año. Quién quiere
  hacer 3P sale de la respuesta mensual `preferencias.tercerPuesto`, no de una tabla de altas, y **todo lo que INV-8 necesita lo deriva el
  dominio con `thirdpost.js:thirdPostVolunteersFromPrefs`** —`periodos` para 8a, `voluntarios` con
  `desde` = inicio del año de residencia para 8b/8c, `delMes` para repartir—: no lo reconstruyas en
  el invocador: servidor (`thirdPostForMonth`) y cliente (`estadoVoluntariado3P(mes, anio)`) lo
  piden por la misma vía para no juzgar cosas distintas. El rango que hay que leer lo da
  `thirdPostHistoryStart`, igual que `rotationHistoryStart` para C-2. Y el historial que se le pasa
  debe contener **solo los 3P anteriores al mes** — los del mes llegan por `asignaciones`, y
  contarlos por las dos vías rompe el ciclo de siete días. Y `asignaciones` es el mes **entero**, no
  solo sus 3P: 8d (mochila) y 8e (V-58) leen las G/GF/GP de cada día, y sin ellas callan. La tabla `voluntarios3P` (altas con
  compromiso de 4 meses, V-18) ya no se lee ni se escribe: se conserva por historial.
- **Los dos cierres de INV-3 se invocan desde `marcarValidado` (servidor) y `Calendar.jsx` (vía `client/lib/closes.js`), no desde `validateMonth`.** Quien añada otra pantalla que valide un mes tiene que llamar también a `closes.js`, o la equidad de cierre no se comprueba ahí. Lo mismo con INV-8, que tampoco está en `validateMonth`: `validateThirdPost` en el servidor, `client/lib/thirdpost.js:thirdPostViolations` en el cliente. Los rangos que hay que leer los dan `quarterCloseWindow` y `yearCloseHistoryStart` — no se adivinan (mismo error que costó la regresión de C-2). Desde V-48 el cierre anual compara también con los compañeros de cohorte que cerraron ese mismo año en un mes anterior (`equity.js:earlierClosedPeers`), y `yearCloseHistoryStart` ya incluye sus ventanas: si cambias quién cierra o con quién se compara, cambia esa función y no el filtro del invocador.
- `cohorte` (calendar year of `fechaInicio`: INV-3's two closes, INV-6, INV-8c, INV-11) and `nivel` (date-derived level, used for MAYOR/PEQUENO) are distinct — don't conflate them. `blockPreview.js`'s concentration-risk axis (P-13) groups by `nivel` (R1–R4) on purpose, while INV-6's own "max 2 simultaneous" groups by cohorte, counting `absences.js:AUSENCIA_SIMULTANEA` (never BAJA): they look identical from outside while measuring different things.
- **P-13 blocks only inside a 3-month window (`previewWindowEnd`, `blockPreview.js`).** Absences are sometimes requested a year ahead, already cleared with tutoría; blocking them would leave them unregisterable though things can still change before they enter the window (which mirrors the ~3-month cuadrante-building session). Outside it the same imposibilidad risk is only `aviso` — an explicit author decision (spec.md §8.1): don't "simplify" it to always-block. BAJA never feeds `blockPreview.js` at all (it's unpredictable and INV-5 already forbids any guardia on it; INV-6 doesn't count it either).
- **C-3 (ventana de `puentesLibres`):** el eje `puentesLibres` de INV-3 compara el **año de
  residencia entero**, no el mes: los puentes se derivan de los festivos (V-61) con
  `calendar.js:bridgesBetween` sobre `[aniversario, aniversario+1año)`, que **cruza dos años
  naturales** (el aniversario cae en mayo). El rango de festivos lo da
  `equity.js:yearCloseFestivosRange` (como `yearCloseHistoryStart` el de asignaciones): no se
  adivina en el invocador (C-2). Son los **años naturales completos** que toca la ventana (±1 día),
  no la ventana recortada, a propósito: si falta el calendario el cierre **avisa de que el eje no se ha podido comprobar**
  en vez de comparar ceros, y la pregunta es «¿está cargado el año 2027?», no «¿hay algún festivo
  en la ventana?», porque la ventana cruza dos años y un `domain.gs` anterior a V-61 solo trae la
  tabla, cargada por año. El aviso solo se emite cuando el invocador pasa
  `festivos` y cuando quien cierra este mes
  tiene con quién comparar el eje: otro de su cohorte que cierra ese mismo año de residencia
  este mes o que lo cerró en los doce meses anteriores (V-48).
- **Festivos (V-61):** la base de la Comunitat Valenciana la calcula `holidays.js:valencianHolidays` y
  `router.js:festivosEfectivos` la une a la tabla `festivos`: una fila activa gana a la base de su fecha, una
  anulada la quita (id `auto:<fecha>` para anular un automático). **No leas `festivos`/`allFestivos`
  directamente**: usa `festivosEfectivos`/`festivosInRange`, o un año sin cargar vuelve a parecer sin festivos.
  Locales de Alicante y traslados siguen siendo manuales (revisión anual, V-63).
- **Los 15 invariantes están implementados.** Dos matices antes de dar algo por comprobado:
  **INV-13 (Imaginaria) NO lo comprueba `validateMonth`** y es deliberado — es una herramienta que
  dice a quién llamar (`imaginaria.js:imaginariaQueue`), no una validación a posteriori, porque una
  incidencia se resuelve por teléfono y el registro se hace después (V-20b). Y **INV-10 depende de una tabla que no se rellena
  sola** (`eventos`): la carga a mano cualquier residente, a propósito, en Ajustes → «Datos del servicio»
  (`DatosServicio.jsx`), como los festivos locales; sin filas, INV-10 no emite nada.

Style: identifiers/code in English, comments/JSDoc in Spanish, explaining *why* (spec.md cross-references), never *what*. Never add an npm dependency under `v2/domain`.

### Server (Google Apps Script Web App: `server/src/*.js`, `server/Code.gs`, `server/domain.gs`, `server/server-lib.gs`, `build/build-gas.mjs`)

Hexagonal design: `server/Code.gs` is the **only** hand-written, impure file — the sole adapter touching `UrlFetchApp`/`SpreadsheetApp`/`LockService`/`CacheService`/`PropertiesService`/`Utilities`/`ContentService`/`MailApp`, and the only backend file with zero test coverage (verify it manually). It builds a `deps_()` object and hands it to the pure `Server.handleRequest(rawBody, deps)` from the generated bundle, which is how `router.js` stays testable without touching real Sheets/Google APIs. `deps.domain` is the **whole** generated `Domain` object, not a hand-listed subset: a hand list meant re-pasting `Code.gs` whenever the domain grew, and forgetting gave a `… is not a function` in production (2026-07-26, `quarterCloseWindow`). Adding a domain function therefore needs `npm run build` and a fresh paste of `domain.gs` only — never `Code.gs`. A new **port** in `deps_()` is the opposite: it needs `Code.gs` re-pasted (and, for a Google service the project never used, its OAuth scope authorized once by running `doGet` from the Apps Script editor before «Nueva versión» — `Code.gs:doGet`, `server/README-deploy.md`), and `router.js` must degrade when it is missing, as with `deps.sendMail`/`deps.llm`, so a newer `server-lib.gs` over an older `Code.gs` doesn't throw.

**`server/domain.gs` and `server/server-lib.gs` are generated artifacts — never hand-edit them.** Both carry a "NO EDITAR A MANO" header. Edit `v2/domain/*.js` or `server/src/*.js` and run `npm run build`; `v2/domain/test/parity.test.js` re-executes the committed bundle in `node:vm`, diffs it against the live ESM source, and fails the suite if they've drifted. The bundler exists because Apps Script concatenates all `.gs` files into one global scope with no ESM, and naive concatenation collided silently (two different `periodsOf`: with hoisting and unspecified parse order, whichever loads last wins, no error). The bundler wraps each module in its own IIFE and only supports a narrow import/export subset (`import {a,b} from "./x.js"` on one line, no `as`; `export function|const|var|class NAME`, one declaration per statement — no `export let`, no default export, no re-export, no dynamic `import()`); anything else fails the build loudly.

Auth flow: client gets a one-time nonce (`getNonce`), runs Google Identity Services, then the server's `verify-token.js:verifyTokeninfo()` validates the ID token — including **manually checking `aud === clientId`**, since Google's tokeninfo endpoint does not itself validate audience ("el fallo estrella" — without it any token minted for another Google OAuth app is accepted). On success the server issues its own signed-not-encrypted HMAC-SHA256 session token (`session.js`); `rol` is always derived server-side, never trusted from the client: `responsable`/`residente` from the `responsables` mandate table, `invitado` (V-53) only when an approved guest request is redeemed. The same secret signs the `pendingToken` and `solicitudToken`, so `router.js:authed` requires a non-empty `sub` in positive — keep it so. Guests are read-only behind a **deny-by-default** whitelist, `INVITADO_ACCIONES` (their `session.rol` can be trusted). Before whitelisting an action, check what it returns: residents go through `paraSesion` (drops emails, fills the period gaps that date a long leave), assignments through `asignacionesParaSesion` (drops V/R/B/C marks); neither covers `bloqueos`, preferencias or imaginaria, which V-53 keeps from guests. The client only hides (see «Client»).

Storage (`sheets-schema.js` + `sheets-store.js`): every table in `sheets-schema.js:TABLES` is append-only and never rewritten row-by-row; `readLatest(table, keyFn)` projects "current state" as last-row-wins per the key the *caller* picks (`id`, or a natural key such as `router.js:ASIG_KEY`); an assignment is deleted by appending its key with `codigo: ""`, so every `asignaciones` reader passes `{ emptyField: "codigo" }` to `readLatest` — without it an emptied cell comes back as a record and «empty cell» checks (`guardarAsignaciones`' 3P rule) misjudge it. `rowsToRecords` maps by column **position** and a sheet keeps its original header, so a new column always goes **last** and a retired one stays: inserting or removing one mid-table silently shifts every historical row. All writes serialize through one Apps Script script lock (a per-user lock wouldn't serialize anything since "Execute as Me" runs everything under one identity). A check whose write must not race another writer goes inside `router.js:atomico` (reentrant per store). The store memoizes sheet reads per request and **empties the memo when it takes the real lock** — otherwise a re-check under the lock reads its own stale copy and overwrites another execution's edit. `Code.gs:withScriptLock_` must `SpreadsheetApp.flush()` before `releaseLock()` (untested). Projected/derived sheets (the `YYYY-MM` tab plus the per-course `Resumen` and `Contaje Trimestral`, V-25; `router.js:projectCuadranteToSheets`) are republished via a crash-safe shadow-swap (`_tmp_` sheet → delete old → rename) — this is only for projected output, never for the append-only data tables. **Fixed production bug worth remembering:** Sheets silently converts an ISO date string to a Date on write, so `sheets-schema.js`'s `"date"` type apostrophe-prefixes on serialize and on deserialize accepts both the string and a real `Date` (read with *local*-timezone getters, matching `Code.gs`'s Europe/Madrid — deliberately not the domain's UTC). Since 2026-09-04 **every plain-text column gets the same apostrophe** (`setValues` also runs a leading `=` as a formula and converts date- or boolean-looking text: a `notas` of "15/7" came back as a `Date`), and `deserialize` strips one leading apostrophe, so the test fakes never emulate Sheets' stripping. `rowsToRecords` also drops rows whose every cell is empty (a hand-cleared row, never a record).

**Generador con IA (`generarCuadranteIA`, V-45/V-47):** el modelo propone y el validador dispone, siempre. Desde V-47 tiene dos modos y el defecto es `completar`: las guardias que YA están en la rejilla (G/GF/GP/3P) son inamovibles —los residentes apuntan en su fila las que ya tienen comprometidas antes de generar—, van al prompt como «ya fijadas», el validador juzga el mes RESULTANTE (fijadas + propuesta) y `apply.js:monthCompletionPlan` nunca emite una fila de borrado. `reemplazar` es lo de V-45 (`monthReplacementPlan`): sustituye solo las G/GF/GP del mes. No hay marca «fijada» en ninguna tabla: una guardia fijada es una fila de `asignaciones` como cualquier otra — no inventes un campo para distinguirlas. Desde V-59 hay además dos **fases** (`fase`): `obligatorias` (defecto) es lo anterior —solo en BORRADOR, y un 3P nuevo es FORMATO (repetir uno ya fijado no en `completar`, sí en `reemplazar` aunque el prompt lo pida: bug abierto)—; `extras` siempre es `completar`, solo añade y no cambia el estado de un mes VALIDADO (los `!extras` de `handleGenerarIA`). Sus reglas de reparto (una guardia extra solo en un día con una sola persona; 3P solo cuando todos los días del mes tienen ya dos) son rechazos FORMATO del router, no invariantes. El cliente ofrece `completar`/`extras` solo si `estadoCuadrante` los anuncia (`modosGeneracion`/`fasesGeneracion`). El modelo se llama fuera del lock; dentro de `atomico` se relee el mes y se vuelve a juzgar: no saques esa relectura de ahí. Y el ciclo no empieza un intento que no le cabe antes de los 6 minutos con que Apps Script mata la ejecución (V-64: `deps.relojMs`, `LIMITE_GENERACION_MS`, resultado `TIEMPO_AGOTADO`): una ejecución muerta no contesta JSON sino una página de Google sin CORS, que el navegador ve como «blocked by CORS policy».

**Excel del servicio (`volcarContaje`, V-65):** el contaje oficial se escribe en una Hoja aparte (propiedad `CONTAJE_SPREADSHEET_ID`) a través del puerto `deps.contaje` — `Code.gs:contaje_()` en producción, `server/contaje-memoria.mjs` en tests y dev-server (`GET /__contaje` enseña lo escrito). Es `null` sin la propiedad y entonces todo funciona como antes. Al publicar va en un **segundo** `atomico`, después del de la publicación y nunca anidado, y nunca la bloquea ni la revierte (`contajeExcel` en la respuesta); despublicar no lo toca (V-11b), aunque el siguiente volcado del curso deja fuera el mes despublicado (solo cuentan los PUBLICADOS de ese momento). QUÉ se escribe lo decide `contajeExcel.js`; el adaptador solo abre, lee y aplica a ciegas — si el Excel cambia de forma, se cambian el plan y sus huellas, no el adaptador. El adaptador lee con `getDisplayValues` y guarda por ejecución cada hoja y el tamaño de su rejilla (una lectura en medio de escrituras es un viaje con el lock cogido); ninguna combinada del plan puede cruzar las columnas fijadas, y el doble lanza como Sheets si lo hace.

Deployment must be "Execute as: me" + "Anyone" access, or CORS breaks (see `server/README-deploy.md`); redeploy via "Nueva versión" on the existing deployment, not a new one, or the `/exec` URL changes.

### Client (`index.html`, `client/loader.js`, `client/config.js`, `client/lib/*`, `client/ui/components.jsx`, `client/App.jsx`, `client/screens/*.jsx`)

No bundler, no build step. `index.html` loads React/ReactDOM/GIS from CDN tags plus one `<script type="module" src="client/loader.js?v=YYYYMMDD">` — **bump that `?v=` on every `loader.js` change**: Pages caches it 10 minutes, so a new `index.html` would run the old loader. `loader.js` exists because Babel Standalone's `<script type="text/babel">` scanner silently dropped one JSX file: it fetches (in parallel), transpiles and `import()`s each file from a `Blob` URL sequentially, in a fixed order (`components.jsx` → screens → `App.jsx` last, since `App.jsx` consumes `window.Screens.*`). Since 2026-09-04 the transpiled output is cached in `localStorage` keyed by the SHA-256 of each source file, and Babel Standalone (~2,3 MB) is injected by `loader.js` only when some file misses the cache — `BABEL_URL`/`CACHE_PREFIX` in `loader.js` are the single place to bump its version. `loader.js` also prefetches the login nonce (`auth.js:prefetchNonce`) before any screen exists. Since 2026-10-07 Babel runs with the `react` preset only (no `preset-env`: the untranspiled `client/lib`/`v2/domain` modules already require ES2020, and ES5 output made transpiling ~4x slower on phones); `index.html` ships a static boot screen inside `#root` (its text rewritten by `loader.js` while transpiling) that `ReactDOM.render` replaces; and `index.html` preloads every `JSX_FILES` entry (`<link rel="preload" as="fetch" crossorigin>`) plus their whole native import graph (`<link rel="modulepreload">`) so a cold start is one parallel round trip instead of a ~8-deep waterfall. **Adding or removing a `client/lib`/`v2/domain` import from the client means updating those `index.html` lists** — `test/precarga.test.js` walks the real import graph and names what to add or drop.

Two rules this creates, both easy to violate without an obvious error:
- **Every import inside a `.jsx` file must be root-relative** (`"./client/lib/api.js"`, `"./v2/domain/calendar.js"`), never relative to the file's own folder — `blob:` URLs are opaque/non-hierarchical, so a same-folder relative import throws once the code executes from a blob.
- **`.jsx` files must never import another `.jsx` file** (Babel Standalone transpiles each file in isolation, no cross-file graph). Cross-screen composition instead happens through global namespaces: `window.UI.*` (components), `window.Screens.*` (screens + `Screens.App`), and `window.useApp` (App's context hook). Plain `.js` modules under `client/lib/` and `v2/domain/` are real ES modules and can import each other normally. Adding a new screen means appending it to `loader.js`'s `JSX_FILES` before `"client/App.jsx"`, plus its `<link rel="preload" as="fetch" crossorigin>` in `index.html` (`test/precarga.test.js` checks).

There is no React error boundary: any exception during render blanks the whole app until a reload (so far: a hook after an early `return`, a field of still-`null` state, `parseISO` on a half-typed date input — use `client/lib/fechas.js:fechaValida`/`rangoValido`). No test catches this — open the screen against `server/dev-server.mjs` before merging.

`client/config.js` holds `EXEC_URL` and `GOOGLE_CLIENT_ID` as committed, non-secret constants (by design — zero secrets in the browser); treat edits to it as deploy-affecting, not routine config. Session tokens live in `localStorage` under `guardias_session` since 2026-10-07 (decision S-8, Quique's call): in `sessionStorage`, a phone's back button closing the tab forced a full Google + Apps Script login. The token still expires alone (12 h, `Code.gs:SESSION_TTL`); `auth.js:getSession` drops an expired one (and migrates a pre-S-8 `sessionStorage` one). Accepted trade-off: on a shared phone whoever picks it up is logged in until expiry or logout. All open tabs share the session, so `App.jsx` listens to the `storage` event to log out (or switch user) everywhere at once. The phone's back button navigates between screens (S-8, `client/lib/navegacion.js`; root model since PR #71): every user-initiated tab change goes through `setTab` (never `setTabRaw`, or back skips the screen); Inicio is the root — going to it unwinds (`go(-depth)`) instead of pushing, so back from Inicio always exits the app; returning to the previous screen is `back()`; logout unwinds to the root; a reload restores the screen from `history.state`. A new screen goes in `loader.js:JSX_FILES` and its preload (above), in the `tabVisible === "…" ?` render chain and in `App.jsx:NAVEGACION.pantallas`; `navegacion.test.js` fails if the last two differ, but sees only that form of the chain: render a screen any other way and back to it silently jumps to Inicio. «Is someone logged in?» is the React state (`authRef`), never `getSession()`, which already returns null for an expired token while the screen is still someone's. Unsaved changes are asked about before leaving (`cambiosSinGuardarRef` for the grid, `prefsSinGuardarRef` for Preferencias) and warned on reload by `client/lib/aviso-salida.js:avisarAlSalir` — `beforeunload` only while they exist (an always-on one breaks the bfcache); reuse it. `client/lib/api.js` sends every request as a CORS "simple request" (`Content-Type: text/plain`, `credentials: "omit"`, identity as a bearer value inside the JSON body) to avoid an OPTIONS preflight Apps Script cannot answer — don't add an `Authorization` header or custom content type. Reads issued together are coalesced into ONE request (S-9, 2026-10-07 — no spec.md row yet; only `api.js`/`router.js` comments and `server/README-deploy.md`): every `/exec` call costs ~3 s of Google startup + redirect even when the execution takes milliseconds, and parallel calls slow each other (21 s seen), so `makeApi` queues the read actions in `LOTEABLES` for 10 ms and sends them as a single `lote` action (server: `handleLote`, `LOTE_ACCIONES`; reads only, max 12, each inner call goes through the whole `handleRequest`, so permissions and the guest allowlist still apply). A lone read goes out as before, and a server that does not know `lote` yet (it is deployed by hand) switches batching off and the calls go separately. A new read action must be added to BOTH sets, server first: an older `/exec` fails that call alone («no admitida en un lote») with no client fallback; no test compares the sets. `callBackend` never throws; all failures normalize to `{ok:false, error}` (an HTML page or a non-object JSON included), and transport ones carry `transporte: true` — for a write it means «unknown whether it was saved», not «rejected» (V-64). It retries only transport failures, and only for the actions in `api.js:REINTENTABLES` — **never add a write there** (a retry duplicates an append-only row). A rejected session is recognised by its exact text (`api.js:isSessionError` vs `router.js:authed`'s `sesión ${reason}`): rewording it silently stops sending users back to login. `makeApi` guarantees that every list read in `CAMPO_LISTA` returns its array whenever `ok:true` — a screen may rely on `if (r.ok) setX(r.lista)`; a field added to an existing action later must still be read with `|| []` and must NOT go in `CAMPO_LISTA`, since an older `/exec` legitimately lacks it. `doGet` is never `ok:true` (`router.js:handleGet`): the client uses POST for everything, so a GET is a POST Google degraded on the way; answering `{ok:true, nonce}` made one look successful.

One more anti-regression convention specific to this layer: assignments are keyed by `residenteId`, never by resident name — `Calendar.jsx` has an explicit note against reintroducing that regression.

Cycle/validation permissions the UI shows (`puedeMoverCiclo`, `puedeValidarCuadrante`, and Home's generator card `vistaGenerador`) come from `client/lib/permisos.js`, a display-only mirror of the server (V-16) — never re-derive one inline in a `.jsx`; the guest gate is `App.jsx:tabVisible` (local) plus `esInvitado`, which screens read via `useApp`. A new read on a guest's screen (`home`/`calendar`) fails unless whitelisted on the server (see «Auth flow»): whitelist it only if it exposes nothing V-53 hides; otherwise skip the call behind `esInvitado`, as `Home.jsx` does with `Imaginaria`. `auth.js:perfilDelToken` decodes the Google token unverified — display only, never identity.

## Where a business rule is allowed to come from

`spec.md` is the single register of domain rules, and it has three parts that must not be confused:
**§5** the invariants in force (`INV-1`..`INV-15`), **§5.1** where each one's authority comes from
(a quoted passage of `docs/normativa.pdf`, or an explicit "extensión sin respaldo normativo"), and
**§8** the register of proposals: a row is in force only once `implementado`, and then as §5, its
`V-n` in §6 and, where it has one (P-1..P-13 except P-11), its paragraph in §8.1 state it — not as the row's own wording (P-15's body still describes the refuerzo V-58 retired).

The rule documents under `docs/` (the `.md` files outside `adr/`) are **proposals**, not behaviour; `normativa.pdf` and the legacy `.xlsm` are the sources of truth spec.md's header names, and `catalogo-diseno.html` is generated. A
proposal does not introduce a rule; it adds a row to §8 citing the `INV-n` it touches. Only on
reaching `aceptado` does §5 or `v2/domain/` change. Read §8 before implementing anything a `docs/`
file describes — several contradict invariants already implemented and tested.

`normativa.pdf` outranks everything, including this file and `spec.md` (§0),
save departures spec.md records as author decisions: INV-1's §5.1 entry (V-12, a one-person day
is `aviso`; P-14/V-56, so is its composition, «va más allá del texto») and P-10's §8.1 paragraph
(p.3's tutoría and Jefe de Servicio approval is not modelled). None is a spec bug or gets
reverted (V-14); a new departure needs its own §5.1/§6 entry, never a silent change.
When a proposal and an implemented invariant disagree, the question is not who wrote which, it is
what the normativa says — and it does not always side with the code: §8 records it backing P-8
and P-10 «en la letra» (above); P-7 only seemed to and was rejected (V-15).

`test/docs-trazabilidad.test.js` enforces the mechanical half of this and runs inside `npm test`:
every invariant in §5 has a procedencia in §5.1; in §8, every cited `INV-n` exists in §5 and every
state is valid — only on rows whose state cell is bare (P-1..P-9 today; text after the state skips
the row, so keep new ones bare); and **no top-level `docs/*.md` cites a `.md`/`.docx`/`.pdf` whose basename exists nowhere in the repo** (spec.md, this file, `docs/` subfolders and code comments are not scanned). That last one matters most: the AI-assisted `docs/` proposals cite ten documents that never
existed here (`VACATION_IMPACT_MODEL.md`, `DOMAIN_MODEL.md`, a `.docx` rule catalogue…).
Plausibility-generated citations are the characteristic failure mode — the existing ones are frozen
as known debt in the test, and any new one fails the suite.
The test checks traceability, never semantics: it cannot tell that weighted-points equity
contradicts `dif ≤ 1`; that needs a person.

## Branch / deploy model — two people push here concurrently

`main` is both production and the shared trunk: GitHub Pages serves `index.html` from `main`, and **every push to `main` deploys live to the residents using the app**. There is no staging environment. Note that a live deploy is not limited to `client/` — the `.jsx` screens import `v2/domain/*.js` straight into the browser, so a half-finished validator change on `main` is immediately what residents run. (`server/*.gs` is the exception: it reaches `/exec` only when someone pastes it in and creates a «Nueva versión», or runs `npm run deploy`.) What `/exec` serves is known only from the hand-kept «Qué corre HOY en el `/exec`» table in `server/README-deploy.md` — neither `main` nor the editor (HEAD) tells you: add a row on every real deploy, or a «Pendiente de desplegar» line when your PR changes the `.gs` without deploying. `/exec` can lead `main` as well as lag it, so each side must tolerate the other's previous version: the client reads a later response field defensively (`|| []` or feature detection, never `CAMPO_LISTA`: see «Client») and offers a new request option only when the server advertises it (`Home.jsx`: `fasesGeneracion`, see «Generador con IA»; an older server silently ignores unknown parameters); the server treats every new request field as optional, missing = old behaviour unless that destroys data (`handleGenerarIA`: no `fase` = `obligatorias`, but no `modo` = `completar`, not V-45's `reemplazar`).

Two collaborators commit to `main` in parallel. Since PR #45 both work the same way — Claude Code sessions on short `claude/<slug>` branches, mostly PRs each merges himself, unreviewed:
- **Quique** (repo owner, `Molecule97`) and **Agustín** (`aguslagio24`) both touch everything, backend and hand `/exec` deploys included (Agustín's PRs: V-53 #55, S-9 `lote` #67, runbook rows for versions 18/20 #65/#68).
- Agustín still originates most new business rules and the app design.

So assume any file, `v2/domain/` and `server/` included, may have moved under you.

Consequences worth internalizing, because getting them wrong has already cost real work:
- **Always `git fetch` and check `origin/main` before starting anything and again before pushing.** `main` moves without warning.
- **A new `V-n`/`P-n` in spec.md is provisional until your PR merges**: parallel branches each take «the next one» and have collided several times. Re-check `origin/main` right before merging; if you merge second, renumber only your own decision, hit by hit (`git blame`), never a blind replace.
- **At the start of a session, read what changed since you last saw the repo** (`git log --oneline -15`, and `git log -p` on anything surprising) instead of assuming the state described in this file or in memory is still accurate. New rules no longer arrive as `docs/` proposals: they land straight in spec.md (§8 `P-n` and/or §6 `V-n` rows), often implemented the same day (P-14..P-17 on 2026-10-07), and occasionally retired within hours (V-58 retired V-56's `REFUERZO`). So read `git log origin/main -- spec.md` and the newest §6 rows first; an old `docs/` proposal is still not implemented behaviour.
- **Never resolve a divergence between `main` and another branch by overwriting a whole tree** without first checking, file by file, what only exists on the other side. The 2026-07-24 cutover nearly deleted five merged PRs of Agustín's design documents this way; only a non-fast-forward rejection stopped it.
- Nothing in the repo prevents a conflicting edit or a direct push to `main` (see «CI» below), so prefer a branch and a PR whenever a change is not trivially safe to deploy.

**CI (`.github/workflows/test.yml`, added 2026-08-08):** runs `npm test` on every push to `main` and every PR, with zero setup. It catches the mistake that already happened twice: forgetting `npm run build` (bundle parity, `v2/domain/test/parity.test.js`) or `npm run catalogo` (design catalogue freshness, `test/catalogo.test.js`) before pushing. It does **not** block a merge by itself — that needs a branch protection rule requiring the `test` check (Settings → Branches, repo-admin access a coding agent may not have) — so red CI is a strong signal to fix before merging, not a hard gate.
